OVERVIEW
--------
This walkthrough demonstrates how NXNW ingests OnTrack Rogue Valley's client
and services files, de-duplicates those records against other agencies already
in the system, assigns persistent Master Person IDs (MPIs), and exports the
final Golden Records file for use by county commissioners and public health
staff.

OnTrack is the largest SUD/MH treatment provider in the Rogue River Valley,
operating outpatient, IOP, day treatment, residential, and transitional housing
programs from locations in Medford, Ashland, and Grants Pass.

For this walkthrough, OnTrack is bringing in:
  ontrack_clients.csv   — 240 client demographic records
  ontrack_services.csv  — 2,999 service encounter records

================================================================================
  STEP 5 — Stage 2: Standardization & Cleaning
================================================================================

The app now cleans every record to make comparison fair across agencies.
Different agencies use wildly different formats for the same data.

What gets standardized:

  NAMES
    "BRANDON"         →  "brandon"   (lowercased for matching)
    "RAYMOND"         →  "raymond"
    "Mary"            →  "mary"
    Punctuation and special characters stripped.

  DATES (all normalized to YYYY-MM-DD)
    "07/23/1986"      →  "1986-07-23"
    "05/16/1957"      →  "1957-05-16"
    "2/17/73"         →  "1973-02-17"
    "2026-02-10"      →  "2026-02-10"   (already correct)
    "UNKNOWN"         →  NaT (blank — cannot be matched on)
    "2026-01-01"      →  kept (year-only approximation)
    "03/22/2026"      →  "2026-03-22"   (service date example)

  SSN LAST 4
    "201"             →  ""   (3-digit entry — fails \d{4} regex, treated as blank)
    "967"             →  ""   (same)
    "4488"            →  "4488"
    "8279"            →  "8279"
    "REFUSED"         →  ""

  Agentic check after cleaning:

================================================================================
  STEP 6 — Stage 3: Probabilistic Matching (Splink Engine)
================================================================================

The app now compares every record against every other record to find likely
duplicates — the same person appearing at multiple agencies or multiple times.

Splink uses a set of blocking rules to focus comparisons on plausible pairs:
    • Same date of birth
    • Same last name (cleaned)
    • Same SSN last 4 (when not blank)

Then for each candidate pair, it calculates a match probability (0.0 to 1.0)
based on agreement across all fields:

  Comparison                       Weight (approximate)
  ---------------------------      --------------------
  Last name exact match            High
  Last name Levenshtein ≤ 1        Medium
  First name exact match           Medium
  First name Levenshtein ≤ 2       Low-Medium
  Date of birth exact match        Very High
  SSN last 4 exact match           Very High

Example match candidates produced (OnTrack records involved):

  Record A                              Record B                              Probability
  ------------------------------------  ------------------------------------  -----------
  ONTRACK_RV::OT-000142                 ACCESS_HUD::ACC-031                  0.9412
  (Robert Smith, 1978-11-02)            (Bob Smith, 1978-11-02)
  → Same DOB, last name exact, first name is nickname variant

  ONTRACK_RV::OT-000089                 ROGUE_RETREAT::RR-0057               0.8834
  (Maria Garcia, 1992-06-30)            (Maria Garcia, 1992-06-30)
  → Same DOB, same name — likely the same person at two agencies

  ONTRACK_RV::OT-000214                 ROGUE_RETREAT::RR-0044               0.5103
  (James Johnson, 1978-01-01)           (James Johnson, 1979-03-12)
  → Same name, DOB differs — presented in swipe deck for human review

Records with match probability below the minimum threshold are auto-rejected
and never shown in the swipe deck.

================================================================================
  STEP 7 — Stage 4: Graph Clustering & Identity Assignment
================================================================================

Every match above the confidence threshold adds an edge in a graph where each
node is a record and each edge is a potential match. NetworkX then finds all
connected components — groups of records that are probably the same person.

For each connected component (cluster):
  1. Sort the member record IDs alphabetically (deterministic)
  2. Generate a UUID v5 from the sorted member list + "rogue_raise_2026" seed
  3. Assign that UUID as the Master Person ID for every record in the cluster
  4. Average the edge weights to compute the cluster's overall match confidence

This means the same group of records will always generate the same UUID,
even if the pipeline is re-run on different hardware or at a different time.

After clustering:
  • Every unique_record_id has exactly one master_person_id (no orphans)
  • Records that matched nothing become their own single-record cluster
    with match_confidence = 1.0 and match_type = "Direct_Single"

  ✓ Agentic Check: Every unique_record_id assigned exactly one master_person_id

================================================================================
  STEP 8 — The Swipe Deck (Human Review of Match Candidates)
================================================================================

The app presents match candidates above the minimum threshold in a side-by-side
comparison view. The human reviewer sees Record A and Record B and decides
whether to Accept or Reject the proposed merge.

Example card pair — OnTrack record vs. ACCESS (HUD) record:

  ┌─────────────────────────────────┐  ┌─────────────────────────────────┐
  │  RECORD A                       │  │  RECORD B                       │
  │  Source: ONTRACK_RV             │  │  Source: ACCESS_HUD             │
  │  ID:     OT-000142              │  │  ID:     ACC-031                │
  │                                 │  │                                 │
  │  First Name:  Bob               │  │  First Name:  Robert            │  ← Amber (mismatch)
  │  Last Name:   Smith             │  │  Last Name:   Smith             │  ← Teal  (match)
  │  DOB:         1978-11-02        │  │  DOB:         1978-11-02        │  ← Teal  (match)
  │  SSN Last 4:  ----              │  │  SSN Last 4:  3847              │  ← Amber (one missing)
  │  Source:      OnTrack Medford   │  │  Source:      ACCESS HMIS       │
  │  Program:     Outpatient SUD    │  │  Service:     Emergency Shelter │
  │                                 │  │                                 │
  │  Match Score: 94%               │  │                                 │
  └─────────────────────────────────┘  └─────────────────────────────────┘

        [ ❌  REJECT ]                        [ 💚  ACCEPT ]

  Match Evidence:
    Last name    Smith    = Smith         ✓ Exact match     (high weight)
    DOB          1978-11-02 = 1978-11-02  ✓ Exact match     (very high weight)
    First name   Bob     ≈ Robert         ~ Fuzzy match     (nickname variant)
    SSN last 4   (blank) ≠ 3847          ✗ Cannot compare  (one record missing)

  The plain-English summary reads:
  "Strong DOB + last name match. First name is a likely nickname variant
   (Bob / Robert). SSN unavailable on OnTrack record."

  What each button does:
    ACCEPT  → Validates the NetworkX edge. Both records are merged under
              the same Master Person ID. Bob Smith at OnTrack and Robert
              Smith at ACCESS HMIS are now one person in the count.

    REJECT  → Severs the NetworkX edge. The penalty is logged to adjust
              future matching weights. Both records remain as separate
              master persons.
